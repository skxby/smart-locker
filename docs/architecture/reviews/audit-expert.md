# 独立前置审计：阶段 0 契约与放行门槛

日期：2026-10-20。审计对象为工作区 README、`docs/项目计划.md`、材料清单和阶段 0 架构草案。当前没有产品实现，本文不把文档走查称为真机测试，不把采购预留称为成交价。

本文是设计评审输入。开发 AI 的执行依据应是统一的阶段 0 主规格和机器可读契约；主规格应明确采纳或拒绝本文建议，不能同时留下两套冲突规则。本审计仅修改本文件，不实现固件、服务或 App。

## 1. 总体意见

项目适合按一个柜格做成可验证的系统，但现有计划还不能直接拆给多个 AI 编码。最大风险不是缺少页面，而是不同 AI 对“接受请求、实际动作、物品事实、业务完成”使用了不同含义。

阶段 0 应冻结所有权、状态机、证据条件和接口失败语义；板型、Flash 型号、锁脉冲和 ADC 阈值可以保留为必须通过硬件核实的参数。没有核实的硬件参数不得被 AI 用“常见默认值”悄悄代替。

优先级定义：P0 为冻结开发契约前必须消除的歧义；P1 为进入真实执行器联调前必须闭环的风险；P2 为交付前必须验证或明确限制的事项。这里的 P0 不表示已经发现可被利用的产品漏洞，因为当前尚无实现。

## 2. 主要发现与建议处置

| 编号 | 级别 | 当前不完整或易误读处 | 推荐冻结的规则与证据 |
|---|---|---|---|
| A01 | P0 | “柜格状态”可能把库存、操作、门、物品、健康混为一个字段 | 分开定义业务库存、活动操作、物理快照、健康/核对状态。工具可借不能单由物品在位推导；存在未决借用或证据冲突时不能可借。 |
| A02 | P0 | “本人确认+关门+取物”未定义先后、基线、观察完整性 | 每个操作保存开始时物理基线，要求匹配的开门、物品变化、关门证据。建议在门关闭且完整链形成后才接收最终确认；缺失、顺序矛盾或期间事件丢失均待核验。不能用最后一次快照填补历史。 |
| A03 | P0 | “到柜通过触摸屏确认”可能是任何人按一下 | 手机申请人、操作、柜前凭据必须关联。绑定卡仅为原型身份凭据，UID 不具抗复制保证；匿名触摸不能充当本人认证。明确触摸屏是否登录及会话超时。 |
| A04 | P0 | MCU 读卡可能被实现成本地 UID 白名单直接开锁 | RK 是身份/业务权限决策者，MCU 是唯一锁驱动者。读卡只上报事实，必须经 RK 为有效操作授权。首版主机离线不能新借还；已开门操作继续记录并等待核对。 |
| A05 | P0 | App 与 LVGL 两人/多端竞争没有事务语义 | 同一 RK 领域核心串行处理业务，数据库事务保证一个柜格最多一个活动操作；幂等键绑定主体、动作和参数，参数不同即冲突。状态版本必须进入有副作用请求的前置条件，不能只在 App 禁用按钮。 |
| A06 | P0 | 创建操作与发 UART 命令之间可能留空窗 | 操作和待发送意图同事务提交；业务服务崩溃后先核对，不自动重放旧开锁。数据库失败不得先发送硬件动作。接受响应丢失后允许按幂等键/操作 ID 查询结果。 |
| A07 | P0 | UART “ACK”可能被各端理解为开锁成功 | 接受/拒绝、意图已持久化、驱动脉冲开始/结束、门被观察打开、业务确认分别建模。没有锁舌反馈只能报告驱动动作与门观测，不能制造 `LOCK_OPEN_SUCCESS` 事实。 |
| A08 | P0 | 只有 `operation_id` 无法描述一次动作与多次重试 | 借还操作 ID、物理命令 ID、会话 ID、MCU 启动 ID、物理事件序号分别定义。CRC 校验随机传输错误，不承担用户鉴权。UART 作为柜内受控线路的信任假设必须写明。 |
| A09 | P0 | 丢 ACK、重连和重启时可能再次驱动锁 | 同一命令最多开始一次脉冲；重复命令只返回已有结果。任何超时均为结果未知，先查结果。新会话/MCU 启动后旧会话动作必须拒绝。未知执行窗口进入核验，不宣称物理动作严格 exactly-once。 |
| A10 | P0 | ARM 水位检查与真正执行之间仍有竞争 | 解锁绑定单次操作、目标柜格、当前会话、快照版本和短期有效性；控制任务在执行前重新检查门/物品/健康与版本。发生输入变化、会话变化或超时，旧授权失效。不得先 ARM 再无限期等待开锁。 |
| A11 | P0 | littlefs 掉电恢复容易被误认为应用日志已提交 | 先持久化动作意图并收到提交回执，再执行锁脉冲。追加成功入队不等于提交；明确 sync/close 的提交点与错误。挂载失败不得自动格式化继续开锁。 |
| A12 | P0 | 已确认历史日志回收可能同时删除动作去重依据 | 去重/未决意图的保留期限必须独立于普通历史事件；只有旧命令已经被启动/会话栅栏拒绝后才可回收相应去重记录。空间不足禁止新动作，不能回收后允许迟到命令再次执行。 |
| A13 | P0 | “事件序号”不一定能检测队列满前的丢失 | 暴露独立的丢弃计数及连续性状态。若序号仅在成功提交时分配，丢弃不会自然产生序号缺口，不能据此声明日志完整。关键事件丢失立即使相关操作待核验，并阻止新动作。 |
| A14 | P0 | 上电后门/物品快照可能被解释为上轮操作结果 | 启动先关闭锁输出并进入核对；提交新启动标识和复位原因，导入历史至明确水位，对照活动操作与新快照。没有历史就保持未知，不因“当前在位”自动清账。启动标识不能在掉电后重复。 |
| A15 | P0 | 管理员“更正”可能无痕覆盖证据或成为万能开锁入口 | 管理处理是新的带操作者/原因的业务决策记录，保留原始设备事实。管理员处理使用状态版本防并发，不能直接修改历史物理事件。首版不开放普通远程 GPIO 开锁或任意 shell。 |
| A16 | P1 | Flash 擦写、RC522 轮询与锁最长脉冲共用调度 | 控制路径不得等 Flash/SPI；脉冲关闭具有独立有界机制，复位默认关闭。数据提交完成后才动作不意味着动作后要等 Flash 才关断。SPI 总线只有一个仲裁所有者，忙轮询必须让出调度。 |
| A17 | P1 | 冻结新动作仍需保存正在发生的物理变化 | 日志容量保留应急预算，先进入容量告警与禁新借还状态；明确耗尽后如何上报连续性丢失。不承诺有限 Flash 可无限保留离线事件；既有开门不能因存储故障被当成已取消。 |
| A18 | P1 | 监护链路可能通过故障服务请求修复同一服务 | 首版建议仅自动恢复 LVGL；service 失联记录告警，手动/受控重启后核对。不能用 service 的活线程替 UI 主循环递增进度。UI 重启既不重放动作，也不清空活动操作。 |
| A19 | P1 | 多个电源名称易被误写成整体断电仍可工作 | MCU 独立仅指不依赖主机支路，没有电池/UPS；整场停电不能继续记录。UART、ADC 和共地路径均要检查断电反灌，不能验证 UART 后就认为全部信号安全。 |
| A20 | P1 | Android 配对、管理员初始化和目标 ABI 尚未落地 | 明确首次管理员创建/恢复、证书指纹配对、终端发现/手输地址、凭据存储与退出失效规则。TLS 验证失败不能回退 HTTP 或接受全部证书。真实 ABI/TLS/SQLite 编译探针是主机阶段门槛。 |
| A21 | P2 | 195 元是预留且依赖复用，完整工期未实测 | 板型/电源/Flash/工具/网络/柜体复用项逐项确认，发票或订单成本与预留分开。不能为了 200 元删除保护器件。App、机械和可靠性全量交付不能继续写成保证两三周。 |

## 3. 阶段 0 必须交付的契约

以下是可交给其他 AI 的最小合同，不要求在本阶段实现业务。

### 3.1 领域与证据

- 一处定义角色、柜格、库存、操作状态、操作阶段、物理输入的有效/未知状态、健康和核对状态，不散落多套同义枚举。
- 借用与归还各给一张状态表：进入条件、允许命令、所需证据、超时、取消、错误与下一个状态；完整覆盖未开门、开门未取物、取物未确认、还物未确认、门未关、输入矛盾。
- 明确用户取消只能撤销尚未可能驱动的操作；已发动作是否执行不明不能按“取消成功”释放柜格。
- 固定开始物理基线、完整动作链和最终确认条件。门已关的普通快照不能替代未观察到的开门/取物事实。
- 明确证据缺口、未知传感器、丢事件、Flash 不可用、MCU 重启时何时冻结、谁能解除冻结，以及解除的审计记录。
- 一次操作首版最多一次开锁脉冲；没检测到开门后是否结束以及如何重新开始必须确定，不能隐式重复试锁。

### 3.2 暴露接口

- OpenAPI 可解析且每个暴露操作都定义认证角色、输入约束、结果、错误、是否有副作用、版本/幂等与结果回查方式。
- 认证、工具查询、创建借/还、柜前确认、最终确认、取消、活动操作查询、历史、设备健康、管理员核验各自职责明确；不开放通用开锁/任意数据库编辑接口。
- WS 是变化通知，必须携带资源版本/事件游标；断线或缺口后重新读权威状态。HTTP 响应与 WS 到达顺序不能决定成功与否。
- 未登录、越权、资源冲突、旧版本、重复参数冲突、设备未核对、设备结果未知、存储故障要区分；明确客户端可重试与只能查询的情况。
- App 缓存标记过期，禁止缓存执行命令；界面无法确认结果时显示“核对中/待核验”，不得自行报成功。

### 3.3 串口契约

- 帧格式逐字节定义：版本、方向/类型、长度范围、字节序、ID 编码、CRC 算法/范围；提供至少一条完整可校验样例，禁止用 C 结构体内存作为线格式。
- 规定未知版本/类型、错误长度、半帧超时、CRC 错误、流中重同步、接收溢出和队列满行为，控制内存与解析工作上限。
- 命令表完整覆盖建会话、能力、快照、开始动作/结果查询、事件分页、主机持久化水位确认、健康与时间关联。
- 动作授权绑定启动/会话、操作、状态版本与新鲜度；明确过期帧、旧会话、重放、同 ID 不同参数的拒绝行为。
- 明确接收确认、提交确认、执行事实三层结果；超时不等于没执行；事件补传不会驱动硬件。
- 快照与补取有一致水位。主机完成 SQLite 事务后才确认消费；分页重复幂等，最早保留序号和连续性状态必须可查询。
- 日志确认与去重清理分别规定；不能以“已读 ACK”替代主机已落库，不能以主机已落库认定旧命令安全可重放。

### 3.4 内部接口与所有权

- 列出模块调用方向、唯一所有者、同步返回/异步事件、超时、取消、内存生命周期、线程/任务上下文及阻塞上限。
- RK 领域核心独占业务写入；SQLite 事务与待发送意图同提交；HTTP、WS、串口适配器不能各自修改领域状态。
- MCU 控制模块独占锁 GPIO，日志模块独占文件系统，统一仲裁 SPI；ISR 只提交有界通知。
- 日志 API 返回“已排队”与“已提交”不同结果，队列满、提交失败、容量不足显式传播。调用者不能释放仍被异步任务引用的缓冲。
- 模拟器与真实 MCU 实现同一逻辑端口，模拟模式在能力和 UI 可见；不能让调试模拟路径在真机部署自动启用。
- 所有错误/枚举/命令在机器目录、OpenAPI、C 头文件、串口文档中的对应关系可以静态校验，未实现端口明确标注声明而非可用功能。

### 3.5 交给 AI 的任务卡

- 每张任务卡限定输入契约、可修改目录、输出、不得自行改变的领域规则、模拟/真机证据要求与验收；跨接口变更先提交契约修订，不私自兼容另一套命名。
- 先交付主机领域核心与模拟设备，再分接口/页面/固件，避免 App 和固件独立发明业务状态机。
- 拿不到实际板型、电气参数时可以写抽象接口和模拟验证，不能生成“确定可接”的引脚表或直接开启执行器。

## 4. 契约场景走查与验收矩阵

阶段 0 的通过证据为文档表、消息序列和可解析/交叉一致性检查。下表是后续实现必须保留的回归场景，不要求本阶段伪造测试运行。

| 场景 | 契约必须给出的唯一结果 |
|---|---|
| 两人同时借同一工具；同人手机与触屏重复操作 | 只有一个活动操作；另一个冲突或返回已有操作，无第二次脉冲。 |
| 创建已落库但响应丢失 | 同幂等键回查同操作，不新增操作；同键改参数拒绝。 |
| UART 动作发出后 ACK 丢失 | 查询原命令；重试同 ID 不再驱动；未知进入核对。 |
| 意图已提交、脉冲前 MCU 重启 | 新启动禁止旧命令，未决操作核对，不自动尝试脉冲。 |
| 脉冲开始后、结果提交前 MCU 重启 | 原操作可能执行，不能宣称未执行；默认关闭输出并核对。 |
| 旧会话帧迟到，相关历史日志已被回收 | 会话/启动栅栏仍拒绝，不依赖已回收日志去重。 |
| ARM 后门/物品状态变化 | 版本失配导致拒绝，需新快照和重新确认，不能照旧脉冲。 |
| 门已开、工具未取，用户取消 | 不直接归为可借，依据完整收尾规则确认恢复，或者待核验。 |
| 工具已取但手机未确认/手机离线 | 不自动重新可借；保留占用与未决事实，等待同主体确认或管理员核验。 |
| 没观察到物品变化但重连快照显示离位 | 历史证据不完整，待核验，不补造事件。 |
| 归还时放回其他物体 | 在位检测不能识别真伪，产品明确此边界，不能展示“身份已验证”。 |
| 日志队列溢出、Flash 满或挂载失败 | 报告连续性受损，禁止新动作；保持安全关断和已有状态观察。 |
| RK 导入事件后崩溃、MCU 未收到水位确认 | 重复补传按设备/启动/事件 ID 去重，不能重复完成业务或再次动作。 |
| MCU 重启、旧启动事件仍在日志中 | 按启动分段区分时间和序号，重连不覆盖当前快照，不把单调时间跨启动比较。 |
| App 先收到 WS、后收到 HTTP，或 WS 缺失 | 以服务端资源版本为准；查状态可恢复，不按消息到达顺序逆转状态。 |
| 普通用户调用管理员接口、A 用户确认 B 的操作 | 服务端拒绝，不能仅靠 App 隐藏按钮；拒绝不触发硬件动作。 |
| 过期卡前凭据/旧 QR 或旧触屏会话 | 不得用于另一操作或过期动作；不消费仍可执行的长寿命授权。 |
| UI 卡住但 service 正常 | 记录独立进度停止，受限恢复 UI，活动操作保留。 |
| service 停止/UART 断线而 MCU 正常 | 记录可观察事实并冻结新借还，不推断内核死机，不重放。 |
| 正常反复重启 UI 或 supervisor 自己重启 | 恢复计数不能随目标进程重启清零；限次和冷却规则有明确持久化/重置条件。 |

## 5. 分阶段放行门槛

### 阶段 0 → 阶段 1：可独立交接

- 主规格、领域状态表、OpenAPI、WS、UART、内部接口、错误目录与任务卡齐全；所有 P0 在主规格中有唯一答案。
- 机器可读文件能解析；暴露接口数量与命令/错误目录对得上；C 头文件至少语法检查；串口样例能按文档手工或脚本校验。
- 明确未核实硬件表及其责任人、验证方式；不阻止模拟核心开发，但明确执行器联调前的禁止线。
- 本次输出仅契约设计，不标记“完整功能已实现”。

### 阶段 1 → 阶段 2：主机与模拟设备闭环

- 主机实际可构建/启动，ABI 和第三方依赖有证据；模拟器完成业务/并发/幂等/重启核对测试。
- 暴露接口的权限、参数校验与错误语义经过调用验证；App 无需先成型，接口可由测试客户端调用。
- SQLite 故障、进程退出和响应丢失不能产生第二次执行意图；模拟动作不能流入真实串口。

### 阶段 2 → 阶段 3：执行器与物理闭环

- 真实板型、引脚、电平、电源、保护件、锁规格和固定结构确认，成本重算；完整预算超限如实上报。
- 先无锁负载检查驱动，再有锁测最长脉宽、上电/复位默认关闭及反灌；Flash/读卡繁忙时仍满足关断上限。
