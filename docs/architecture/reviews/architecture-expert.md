# 架构专家评审：阶段 0 的职责、恢复与接口边界

日期：2026-10-20。对象：一个柜格、一件固定工具，STM32F407 + RK3568 + Android。依据为现有 README、项目计划、材料清单及本文末的一手资料。当前工程只有方案和材料文档，尚无业务实现，不能引用既有代码已实现任何能力。

本文是阶段 0 的评审输入；主规格应明确采纳或拒绝下列建议，交给开发 AI 时以主规格和机器可读契约为唯一实现依据。硬件参数未核实不影响先冻结逻辑契约，但不得据此声称真机验收通过。

## 1. 结论与优先决策

推荐保留既定技术栈，采用单体业务核心、明确适配器和三个 Linux 进程。一个柜格不需要微服务、消息中间件、云端或跨设备数据库。

必须先解决三项架构问题：

1. **界面和手机不拥有借还状态**：只有 RK 业务核心能够改变借还账本，MCU 只拥有物理状态和动作执行事实。
2. **监护不能替业务程序证明自己健康**：心跳必须携带来自真实业务循环和界面循环的进度，独立监督进程负责重启；不能只开一个永久递增的心跳线程。
3. **重启时不重放动作**：借还操作、开锁指令和物理事件必须使用不同标识。执行前先提交动作意图，任何无法确定是否执行的旧动作进入核验。

## 2. 部署、线程和任务所有权

### RK3568：三个进程

| 进程 | 唯一职责/资源所有权 | 明确禁止 |
|---|---|---|
| `locker-service` | HTTPS/WS、权限、业务状态机、SQLite、UART、事件补取与核对 | 接收客户端指定“借还成功”；任意 shell 执行；自称能够监督自身死锁 |
| `locker-ui` | LVGL 显示和用户输入；真实事件循环进度；调用同一业务接口 | 直接访问 SQLite、UART、GPIO 或提供另一套借还逻辑 |
| `locker-supervisor` | 启动和监督前两者，记录实例变更，限次重启；经私有本地接口收发健康信息 | 持有业务数据库写权限；控制柜锁；接受手机远程任意进程/命令 |

由现有 init 启动 supervisor，不预设目标 Buildroot 一定带 systemd。supervisor 用 `fork/exec`、受控 PID、`waitpid` 和单调时钟管理固定程序；不以进程名 `pkill`，不接受字符串拼接 shell。supervisor 被结束后 MCU 会失去可验证进度并记录异常；首版不声称所有 Linux 进程都能自行恢复。

`locker-service` 内部采用一个业务执行线程作为 SQLite 连接和业务状态的唯一所有者。CivetWeb 回调线程只做请求边界校验、构造命令并进入有界队列；UART 读取/解析也向同一核心提交事件。业务核心不等待开门、Flash 擦除或 WebSocket 客户端收包。

外部动作请求在 SQLite 中提交操作和待发送动作记录后返回；独立传输部分负责发送，结果通过事件推进状态。SQLite 不可能与物理锁组成原子事务，应以持久化意图、幂等标识和核对流程消化中间状态，不宣称“物理动作 exactly once”。

慢客户端有独立的有界发送队列；队列满则断开并要求重新查询，不能阻塞业务线程。不要直接从业务线程调用可能阻塞的 WS 网络写入。

### STM32：推荐四个任务

| 任务 | 职责 | 不可跨越的边界 |
|---|---|---|
| 控制任务 | 10ms 周期观察门磁、在位与 ADC 状态，推进物理操作，处理锁短脉冲 | 不执行 Flash 擦写、文件系统、网络或阻塞读卡等待 |
| 通信任务 | UART DMA 接收、帧解析、会话、发送队列和协议结果 | 不能绕过控制任务直接写锁 GPIO |
| 外设/存储任务 | 独占 littlefs；统一调度 SPI Flash 与 RC522，提交事件和读卡结果 | 不在 Flash 芯片内部忙等待期间长期占着 SPI 互斥量；不直接完成借还 |
| 健康任务 | 观察关键任务进度、主机和 UI 进度、恢复限制；满足条件才喂独立看门狗 | 不把固定定时中断到来视为所有任务健康 |

四任务方案是有限时间的推荐分组：SPI Flash 与 RC522 共用一个所有者，避免两个调用栈各自争抢总线。RC522 轮询拆成有界步骤，Flash program/erase 后释放总线、轮询 busy；若复用库无法满足该边界，先修改驱动适配层，不让控制任务迁就无界阻塞。

控制与通信的优先级高于存储；队列只传定长消息/有明确生命周期的缓冲索引。DMA ISR 只通知任务并更新接收索引。所有互斥等待都有上限；不在持有 SPI 锁时等待业务队列或日志确认。

锁的最长通电时间由 MCU 本地定时机制限制，并保证复位默认关闭，不能依靠 Linux 定时发“关闭”。具体 10ms 周期是设计目标，真机调度、Flash 最坏时延和锁厂商限制在硬件阶段测量。

## 3. 必须冻结的不变量

1. 一柜格最多一个有效操作；业务账本、物理快照和设备健康分开建模，不能压成一个“柜子状态”枚举。
2. 请求接收、动作意图提交、锁驱动开始、门打开、物品变化和业务完成是不同事实。没有锁舌反馈时不能制造“锁已打开”的事实。
3. `operation_id` 标识借还事务；`command_id` 标识一次物理动作；MCU 启动标识与事件序号标识一条设备事实；主机进程实例另有会话标识。
4. 客户端重试提交相同幂等键；服务端不仅缓存响应，还检查同一键的参数一致性。CRC 只校验传输错误，不承担用户鉴权。
5. MCU 只有在本地前置条件通过、动作意图已经持久化、当前会话合法时才允许锁脉冲。首版每个操作最多一次开锁；失败后需核对并生成新的明确操作，不隐式重试。
6. 动作执行后、结果写入前突然掉电属于不可消除的窗口。恢复时把已提交意图视为可能已执行，拒绝再次执行该 `command_id`。
7. 日志损坏、挂载失败、关键事件丢失或无法保证动作去重时，禁止新开锁；继续锁驱动限时关闭、门/物品观察与故障上报。不得挂载失败便自动格式化并继续业务。
8. Linux 不在线时不开始新的借还，不启用 MCU 离线 UID 白名单开柜；已经开门时继续观察、记录并等待核对。独立监护不等于离线业务授权。
9. 借还完成必须同时具备本人确认、门关闭和匹配的物品状态变化；开门不取物、未确认即取物、状态冲突必须有确定出口。
10. 历史事件补取只能补记事实，不能触发物理动作。管理员处理保留原因和原始证据，不覆盖原始事件。
11. 人在柜前的确认具有操作关联及短期有效性。匿名触摸一下不能代替借用者身份；UID 只作为原型绑定凭据，不能宣称抗复制身份认证。
12. UI 重启、服务重启、MCU 重启互不隐含清空当前借还；默认先进入核对，快照不足时为“未知/待核验”。

### 重连核对边界

建议冻结如下流程，避免另一 AI 仅“读一次门状态”便放行业务：

1. 建立新会话，验证版本和设备身份；RK 进入核对模式，MCU 不接收新的开锁。
2. MCU 通过控制任务生成快照，包含当前输入、活动动作及明确的事件边界；存储完成该边界前事件的提交后才报告可核对快照。
3. RK 补取到该边界，按 `(device_id, boot_id, event_seq)` 去重；每批在 SQLite 事务提交后才推进持久化游标和确认水位。
4. 对照未完成操作和快照；核对期间又变化的状态用后续事件继续推进，不用旧快照覆盖新事实。
5. 无日志缺口、物理状态明确且无未决冲突才开放新操作；否则保持待核验。无法取得历史日志时不能把设备当前状态当成历史事实的替代。

日志容量达到上限时保留未确认事件和未决动作。只回收已获 RK 持久化确认、且不再影响动作去重/恢复检查点的历史段；没有可回收空间就停止新操作。文件系统掉电恢复并不等于应用记录已经提交。

## 4. 最小接口分组

不要让各 AI 自行决定跨模块的失败语义。阶段 0 主规格至少应固定下表每组的请求、结果、错误、所有者、超时、重试与持久化边界；函数名只是建议，由统一契约确定。

| 接口分组 | 调用方 → 所有者 | 最小能力 |
|---|---|---|
| 认证与设备连接 | App/UI → RK | 登录/退出、设备信息、角色、自身会话、证书配对说明 |
| 借还业务命令 | App/UI → RK 业务核心 | 创建借/还、柜前证明、本人确认、取消、查询操作；无面向普通用户的直接 GPIO 开锁 API |
| 查询与订阅 | App/UI → RK | 工具、当前操作、借用历史、故障与设备健康；WS 作为变化提示，断线后重新读快照 |
| 管理核验 | 管理员 → RK | 查看原始事件、带原因核验；维护操作独立建账，不复用无审计的调试开锁入口 |
| 领域核心 | HTTP/UART 适配器 → 业务线程 | 提交命令、应用设备事件、读取不可变快照、核对恢复；不暴露数据库连接 |
| 仓储 | 业务线程 → SQLite 适配器 | 操作与 outbox 同事务提交、设备事件幂等导入、游标、核验记录 |
| 设备端口 | RK → MCU/模拟器 | 建会话、读能力/快照、提交关联动作、查动作结果、分页事件、确认已提交水位、心跳与时间同步 |
| MCU 控制端口 | 通信/传感器 → 控制任务 | 验证动作、输入事件、持久化结果、锁脉冲完成；所有 GPIO 动作仅此一路 |
| 日志端口 | 控制/健康 → 存储任务 | 异步追加、持久化回执、分页读取、保留水位；队列满/存储失败是显式结果 |
| 板级硬件端口 | MCU 任务 → BSP | 读输入/供电、有限 SPI 事务、锁脉冲、时间与复位原因；不向上泄露固定引脚 |
| 本地监督端口 | 服务/UI ⇄ supervisor | 固定程序进度、实例号、受控恢复请求与结果；只在私有 Unix socket/固定管道使用 |

接口统一约束：同步返回表示接收/拒绝，异步结果表示持久化或物理动作结果；调用方不持有回调内临时缓冲；超时不等于取消；副作用超时后先查结果再决定新操作。MCU 和 RK 的内部结构体不得直接 `memcpy` 作为线协议。

## 5. 监护与业务控制的冲突处理

MCU 监护收到 UI 进度停止时，产生“请求恢复 UI”的事实，经仍存活的 service 转给 supervisor。service 自己卡住时，该转发链路不可用，supervisor 以本地独立观察恢复 service；MCU 只记录主机/通信失联。不能声称 MCU 能在 UART 服务停止后继续命令该服务修复自身。

建议 UI、service 各自有真实循环进度，心跳消息明确携带“值、实例号、观察年龄”，不能由中间线程替它们递增。Flash/数据库补传繁忙时仍必须有监护调度预算。

恢复动作只针对进程，不能重发旧开锁；进程恢复前先撤销正在排队但未被 MCU 确认接收的旧会话动作。对已可能执行的动作不猜测取消成功，而是进入核对。

UI 重启不停止 MCU 正在进行的安全动作；如果柜门已经打开，MCU 继续观察。自动恢复限额按目标进程分别计数，并跨子进程重启保留。supervisor 自身重启后应从本地记录恢复冷却/限次信息，不能通过重启监督器绕过重启上限。

## 6. 阶段顺序与本阶段验收

| 阶段 | 输出及放行条件 |
|---|---|
| **0：本次** | 架构所有权、状态模型、REST/WS、串口、内部端口、错误/幂等语义、验收与 AI 任务卡；所有 ID/枚举在统一契约中一处定义，不开始各端业务实现 |
| 1：主机可运行骨架 | 业务核心 + SQLite + 模拟设备 + 契约检查；验证竞争借用、重复请求、取消/超时、重启恢复；模拟器显式标识 |
| 2：单柜格真实闭环 | FreeRTOS、输入、读卡、锁驱动、UART；完成一次真实借还与限时关断；接入真实存储后再验收掉电语义 |
| 3：手机与触摸端 | 共用业务接口，Android APK 与 LVGL 完整操作；服务模拟器可先供界面 AI 并行开发 |
| 4：独立记录与监护 | 双端重启、历史补取、进程恢复、限次、供电记录、Flash 故障与容量；不扩到自动硬复位 RK |
| 5：现场交付 | 一柜格连续使用、故障注入、接线/部署/成本/接口同步、实测报告与演示；模拟与真机证据分别标记 |

阶段 0 要求主规格给出确定答案：创建借还时是否占位、到柜确认方式、未取物如何结束、开门后取消如何处理、确认超时后的归属、重新开始操作的权限、恢复时如何释放/冻结柜格。后续 AI 不能凭直觉添加另一套流程。

阶段 0 的验证宜用静态契约检查、场景走查和消息样例交叉核对，不用“测试通过”暗示固件已经可运行。开发阶段有意义的异常测试包括：提交意图前/后、驱动前/后、RK 落库前/后分别中断；丢响应后重试；新会话收到旧帧；日志写失败；补取边界期间门状态变化。

## 7. 待核实硬件与不阻塞的软件工作

| 待核项 | 可先冻结的软件契约 | 真机前必须确定 |
|---|---|---|
| F407 具体板型、可用 SPI/UART/ADC | BSP 抽象、消息格式、队列所有权 | 引脚映射、总线时钟、板载冲突 |
| 板载/外置 Flash 型号容量 | 提交/错误语义、事件分页、容量告警 | 几何参数、时延、可用空间与保留预算 |
| 锁规格与门磁/在位逻辑 | 传感器枚举、动作状态、最长通电配置接口 | 实际极性、允许脉冲、去抖参数、机械误差 |
| RK 系统与工具链 | POSIX/C API 和构建目录边界 | ARM32/ARM64 ABI、libc、TLS/SQLite 交叉编译、init |
| 电源与 UART 断电保护 | 供电有效性/未知状态、通信会话规则 | 电平、反灌保护、输入电压和 ADC 标定 |
| 手机/局域网 | HTTPS 与证书配对流程、离线行为 | 实际 Android 版本、网络互通、时钟与证书有效性 |

硬件能力在握手中显式上报。缺失 Flash、传感器未知或电源观测无效只能进入相应降级/阻塞状态，不能由开发 AI 默认为工作正常。200 元预算沿用材料清单，不在架构设计中暗增电池、服务器、第二柜格或额外传感器。

## 8. 一手资料与复用判断

- [CivetWeb 官方手册](https://github.com/civetweb/civetweb/blob/master/docs/UserManual.md)：连接由工作线程处理。因此 API 回调存在并发，本文采用业务单所有者消除跨回调事务竞争。复用 HTTP/TLS/WS，禁用不用的 CGI/Lua 等能力；交叉编译和 TLS 依赖另做板端验证。
- [SQLite 线程模型](https://www.sqlite.org/threadsafe.html) 与 [synchronous 配置](https://www.sqlite.org/pragma.html#pragma_synchronous)：库的线程安全不能代替业务并发规则。由一个线程访问写连接，明确事务提交与同步配置；实际存储介质若不遵守同步保证，仍不可承诺物理掉电零丢失。
- [littlefs 官方仓库](https://github.com/littlefs-project/littlefs)：C、BSD-3-Clause，提供掉电恢复机制；文件修改在 sync/close 时提交。应用必须检查返回值、区分已提交事件与排队事件，且不能照搬示例中的“挂载失败即格式化”策略。
- [FreeRTOS-Kernel 官方仓库](https://github.com/FreeRTOS/FreeRTOS-Kernel)：MIT，复用任务/队列/互斥；具体版本在进入实现阶段前锁定。本文不自行开发 RTOS、文件系统、TLS 或 HTTP 服务器。

以上库的存在和维护来源不等于本项目完成适配或安全审计。阶段 0 不写未经验证的性能数字，不把原型称作工业级门禁。
