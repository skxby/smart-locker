## 2. 为什么是 UVC：从既有接口倒推

先看相机在这个系统里到底被要求做什么，选型空间就被压得很窄：

| 既有约束 | 出处 | 对相机的含义 |
|---|---|---|
| 相机 FD、帧缓冲、RKNN context 只归 locker-vision | [视觉架构 §2](../architecture/vision-architecture.md) | 只需一条本机 V4L2 采集路径，不需要厂商 SDK 封装、不需要多路复用 |
| 相机不出现在任何公开 API，只有只读 `/vision/status` 暴露可用性 | [视觉接口 §1](../architecture/vision-interfaces.md) | 不需要 RTSP/ONVIF/网页预览/云端推流能力 |
| 输入固定 224×224 七分类整图 | [视觉架构 §1](../architecture/vision-architecture.md) | 分辨率越高越无用；640×480 已满足“ROI 短边≥448、不放大” |
| 每次 3 帧、帧间隔≥100ms、总截止 3000ms | [视觉接口 §3](../architecture/vision-interfaces.md) | ≥10fps 即可，30fps 有 3 倍余量 |
| 帧到 Core 年龄≤2000ms，且不得用请求前缓冲冒充新帧 | 同上 | 必须能拿到**每帧真实序号 + 单调时钟时间戳**，不能是“dequeue 时刻” |
| 机位/ROI/分辨率变化即新 camera generation | 同上 | 机位必须刚性可复现，镜头不能自动变焦/对焦 |
| 柜内静态、单件工具、近距离 | [视觉架构 §4](../architecture/vision-architecture.md) | 不需要快门速度、不需要 HDR、不需要深度 |

由此得到两条排除性判断：

1. **MIPI CSI 不合适。** RK3568 的 CSI 链路要走 `rkisp` + `csi2_dphy_hw` 设备树、sensor 驱动与 IQ 调试，而本项目连 RK 板的具体型号都还没登记（只记录了“RK3568 板”），CSI 连接器形态、可用 lane、供电与 DTS 全部未知。模组本身 20 元级并不比 UVC 便宜，差价全被调试风险吃掉，而且一旦换板就重做。UVC 只依赖标准 USB-A 主机口与内核自带 `uvcvideo`。
2. **自动对焦不合适。** AF 会在 3 帧之间改变成像几何与清晰度，等于让 pipeline 在采集过程中漂移；固定 ROI 的前提就是固定光学。所以「定焦」或「手动调焦后锁死」都可以，唯独不能要 AF。

## 3. 硬性规格与验证判据

| 项目 | 要求 | 为什么 | 到货怎么验 |
|---|---|---|---|
| 接口 | USB2.0 UVC 免驱（`uvcvideo`），直插 RK 板 USB-A | 免驱动、免 DTS、换板不重做 | `v4l2-ctl --list-devices` 能列出设备 |
| 像素格式 | 至少 YUYV 640×480@30 | 免 JPEG 解码与压缩伪影，带宽约 18MB/s 安全落在 USB2 实际吞吐内 | `v4l2-ctl --list-formats-ext` 必须出现该组合 |
| 分辨率上限 | 720P 足够，不追 1080P | 1080P YUYV 超 USB2 实际带宽，MJPG 又引入解码与伪影 | 同上，确认 640×480 为原生档而非裁剪 |
| 对焦 | 定焦，或手动调焦后上胶锁死；对角 FOV 70–90° | 机位固定、几何可复现；AF 会在三帧之间改变几何 | 装好后调焦到最清晰，点一滴热熔胶固定并拍照记录 |
| 感光 | 彩色 + IR-cut | 模型训练在正常彩色照片上，去 IR-cut 会整体偏色 | 白光下拍色卡/实物，与训练集观感比对 |
| 曝光/增益 | **必须支持手动**：`exposure_auto=1`、`exposure_absolute`、`gain`；白平衡可手动 | 自动曝光在 3 帧之间来回摆动，直接破坏“三帧一致”与质量判据 | `v4l2-ctl --list-ctrls` 能看到并可写 |
| 时间戳 | 每帧 `buf.flags` 含 `V4L2_BUF_FLAG_TIMESTAMP_MONOTONIC`，`sequence` 严格递增 | S2-11 要求证明新帧与 MONOTONIC 映射，不能拿 dequeue 时刻顶替 | 抓帧时打印 flags/sequence/timestamp |
| 供电 | 总线供电，≤500mA，随机约1米 USB-A 线，不经 hub，不与补光同口 | 掉帧与枚举失败多半来自供电和线材 | 连续采集 10 分钟看有无丢帧；量实际线长 |
| 补光 | 5V 白光小灯板，插自有充电头，固定亮度与色温，45° 侧上方 | 分类稳定性依赖固定光照；成套环形灯多为 PWM 调光，短曝光下会出现明暗带 | 锁定曝光后连拍，看亮度方差 |
| 固定 | 4×φ3 孔、孔距 24×22mm；M3 尼龙柱 + 洞洞板/EVA（已有 B13、B16），距工具 25–35cm，俯角 30–45° | 机位是 profile 的一部分，松动等于换相机 | 拍机位照片并入卡内证据 |

一个容易忽略的坑：架构要求“仅用 dequeue 时间无法证明曝光时间时，REQUIRED 不能据此接纳旧缓冲”。所以选型时优先挑**能回读 `exposure_absolute`** 的模组；若实物只提供自动曝光或无法回读，S2-11 只能用“开启流之后才入队 + 序号递增 + 单调时间戳”这条较弱证据链，并必须在卡内写明该限制，不能默认它满足 REQUIRED。

## 5. 到货后的验证顺序

页面详情图已经给出两条有利证据：格式列表里存在 `YUY2`（含 640×480 档），属性面板里「曝光」「增益」「白平衡」都带“自动”复选框——仅作为卖家展示的控制能力线索，不能证明所选SKU固件及Linux controls；预期核对的Linux项为 `exposure_auto`/`exposure_absolute`/`gain`/`white_balance_auto`。但页面不是实测，仍按下面顺序验：

1. `ls /dev/video*`、`v4l2-ctl --list-devices`：确认设备节点与驱动名。不要依赖枚举顺序，用 `/dev/v4l/by-id/` 或 udev 规则固定 `camera_id=slot-1` 的节点。
2. `v4l2-ctl -d <node> --list-formats-ext`：确认 YUYV 640×480@30 原生存在。
3. `v4l2-ctl -d <node> --list-ctrls`：确认 `exposure_auto`、`exposure_absolute`、`gain`、`white_balance_auto` 存在且可写；锁定后读回值不漂移。
4. 抓帧并打印时间线：`--stream-mmap=4 --stream-count=10 --verbose`，核对 `sequence` 严格递增、`timestamp` 单调、`flags` 含 MONOTONIC标志，另外检查TSTAMP_SRC的SOE/EOF和曝光/内部管线界限，不能只凭时钟标志判新曝光。
5. 锁定曝光/白平衡后连拍 3 帧：亮度与 argmax 稳定，才谈得上阈值标定。
6. 拔插与重开：设备消失/重连必须生成新 camera generation，未决采集失效。
7. 机位与补光固定后拍机位照片、记录距离/角度/照度，连同设备节点、格式、控制值写入实际 profile。

任何一步不通过，就换型号或退回兜底分支；不能先标定阈值再补验证。

## 曝光新鲜度的实际门槛

MONOTONIC仅是时钟域，TSTAMP_SRC才区分SOE/EOF。按视觉接口规范，captured_mono_ms应为曝光开始保守下界；EOF/驱动时间必须减去实测并留裕量的曝光+内部管线延迟上界B。B未知、无可验证来源时，不能凭出队时间、重开流或手动曝光读回通过REQUIRED。S2-11保存原flags/timestamp/B、机位profile及实验条件，失败退回选型或保留SHADOW，不自动放宽证据语义。
