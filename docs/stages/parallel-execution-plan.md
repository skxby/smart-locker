# 全项目并发调度方案

范围：契约0.2.1的45张产品卡。本文给出调度方案；实际进度始终重新读取[机器状态索引](../../config/development/stage-plan.json)，本文不覆盖正在运行AI的卡内状态。

## 0. 用户授权与固定分工（长期有效）

用户已正式授权本项目采用「两条开发线 + 一个统一集成负责人 + 独立审计」的并发方式，并要求按第 2、3 节的表格执行（不再默认全串行）。该授权是长期记忆，写在本文件与 `AGENTS.md` 的开发纪律中，后续AI开工前必须读到。

| 角色 | 固定承担者 | 说明 |
|---|---|---|
| 开发A | 主开发会话（当前承担S1-03及之后的主线卡） | 只改本卡分配目录、模块README、正式测试、本卡证据 |
| 开发B | **固定为 DSH 中本项目工作区下新开的那一个会话**，后续不再更换 | 与A同时只改不重叠目录；不写共享文件 |
| 集成负责人M | 由开发A分时担任 | 唯一写 stage-plan、根CMake、契约/生成物、DDL 与跨模块整合 |
| 审计R | 独立审计会话（codex） | 只写 audit*.md 与审计证据，不改业务代码与状态 |

并发执行规则：

1. 只有第 3 节表格列出的窗口才真正并行；表外卡仍按依赖串行，不为占满两条线提前开工。
2. 并行前必须核对：两支前置卡均已 DONE、目录不重叠、共享文件写者唯一；任一不成立就退回串行。
3. 共享文件（`config/development/stage-plan.json`、根 `CMakeLists.txt`、`contracts/`、生成物、`docs/architecture/module-ownership.md`）只由M改；开发B需要时提变更请求，不直接写。
4. 每支仍按本卡4段指令（开发→审计→整改→交接）执行，各自写自己的证据目录，不互相代写报告。
5. 单卡证据门禁不因并发放宽：DONE 仍需真实构建/测试证据，阶段 gate 仍需门禁卡 PASS。
6. 汇合卡（S1-04、S2-05、S3-06）必须等两支都通过才发；缺一支不发。

当前落地状态：S1-01、S1-02、S1-03 均已 DONE（S1-03 由开发A完成，round-9 独立审计 PASS），因此**阶段1 的 S1-02/S1-03 并行窗口已经过去**（实际为串行完成）。下一张 S1-04 尚未开工（`active_task=null`），它是与 S1-05 的汇合卡，须等两支都通过才发。下一个真实可并行窗口是阶段2A 的 S2-03（UART/DMA）与 S2-04（Journal），再之后是阶段3 的 S3-02→03→04 与 S3-05。届时按第5节交接模板发布分配。

## 1. 人员配置与写权限

推荐最多2张开发卡同时运行，加1位集成负责人和1位独立审计角色。角色可以分时由同一工具担任，不要求始终有4个运行中的AI。

| 角色 | 主要职责 | 共享写权限 |
|---|---|---|
| 集成负责人M | 排卡/冻结接口/整合模块/维护根构建和状态 | stage-plan、根CMake/固件工程、正式接口变更的唯一写者 |
| 开发A | 当前分支A实现与模块测试 | 仅分配卡目录/模块README/正式测试/本卡报告 |
| 开发B | 当前独立分支B实现与模块测试 | 与A不重叠的目录，同样限本卡 |
| 审计R | 独立核对已冻结交付，实跑必要测试 | 仅audit.md和审计证据；不同时改业务/状态 |

只有一个开发分支时不硬凑第二张卡。审计可以与另一个模块开发重叠，前提是审计对象版本已经冻结、变更范围清楚；不对正在持续改写的同一批文件签通过。整改后原审计结论须按新文件重新核对。

## 2. 完整产品路线与分配

### 阶段1：主机模拟闭环

```text
M/开发A：S1-01 构建/基础设施
             ├→ A：S1-02 SQLite仓储 ───────┐
             └→ B：S1-03 协议/模拟器 ──────┤
                         两卡验收通过后汇合↓
A/M：S1-04 Core → S1-05 HTTPS/IPC → S1-06装配 → S1-07集成审计
```

S1-02改host/storage；S1-03改host/device、host/simulator。模拟器持自己的SQLite文件，不共用业务库。两卡提供局部构建接入，根CMake只交M；不能各自修改公共DTO/DDL或为了方便复制另一份Core。

S1-04实现时，另一AI可对已冻结仓储/协议补独立审计，不开始需要Core完成的S1-05。S1-07通过才进入正式S2。

### 阶段2A：HAL与实物底座

```text
A：S2-01 BSP → S2-02 输入/SPI
                    ├→ A：S2-03 UART/DMA ──┐
                    └→ B：S2-04 Journal ───┤
                           两卡验收通过后汇合↓
M/A：S2-05 Control/硬截止 → S2-06 RK串口 → S2-07整柜 → S2-08底座审计
```

UART分支拥有transport及通信任务相关文件；Journal分支拥有journal及Flash驱动。共享SPI接口/请求上下文/sink已冻结，修改要交M，不能双方各改同一调度文件。Journal依赖真实Flash几何，缺实物不能把电脑文件后端测试当掉电验收。

S2-05汇合后统一分配任务/队列/定时器，不能一边驱动真锁一边由另一AI更改日志水位、GPIO极性或截止实现。S2-06之后的整机/断电实验同一时间只由一个执行者操作同一套硬件。

### 阶段2B：模型与视觉集成

```text
A/视觉开发：S2-09 资产/等价 → S2-10预处理/量化 → S2-11真实相机
→ S2-12 RKNN worker → S2-13私有IPC → S2-14 Core融合/只读API
→ S2-15真机闭环 → S2-16完整阶段2审计
```

现有依赖下这些卡逐卡相接。不要为了占满两个AI把S2-13提前到worker契约/行为未落实时正式开工。第二AI可审计已经冻结的前一模块，或做明确分配的只读准备工作。

模型转换、板端编译、拍照标定各受不同环境制约，不能把并发数量当精度或时延保证。板端NPU/相机实测由单一实验执行者协调；原E:/equipment-vision保持只读。S2-16才解锁S3。

### 阶段3：Android与LVGL

```text
M/A：S3-01 客户端类型/生命周期
       ├→ A：S3-02 Android配对 → S3-03手机借还 → S3-04管理/变化重查 ─┐
       └→ B：S3-05 LVGL/异步IPC ─────────────────────────────────┤
                                      两支均验收通过后汇合↓
                                   S3-06双端真机 → S3-07审计
```

这里是最有价值的持续并发窗口。A完成S3-02即可进入S3-03，满足单卡交接规则后无需等B的S3-05；同理继续S3-04。B可以在这个期间持续完成S3-05。S3-06须两支都通过，不能因为手机完成就跳过柜屏验收。

A只改分配的app子目录，B只改terminal-ui及其模块测试。客户端公共类型、契约生成与根构建归M；出现服务字段不符不能由两个客户端分别补不同兼容逻辑。

### 阶段4：独立记录与监护

```text
S4-01容量/回收 → S4-02供电 → S4-03进度/IWDG → S4-04观察/健康搬运
→ S4-05固定UI恢复 → S4-06业务接线 → S4-07故障矩阵 → S4-08审计
```

当前是串行依赖。Storage/Control/Health与Core/监督器有连续接线关系，不直接同时发给几个AI改。开发阶段可让R审已冻结模块；故障矩阵必须避免两人同时暂停/重启同一板卡/进程导致实验无法归因。

### 阶段5：现场交付

```text
S5-01制品 → S5-02启动权限 → S5-03维护备份 → S5-04更新回退
→ S5-05现场验收 → S5-06文档/演示 → S5-07最终审计
```

正式卡按当前顺序。文档素材整理可以与开发进行，但S5-06的正式交付必须依据实测事实；不能先生成漂亮指标后等现场测试填数。部署、数据库维护、固件烧录与电源故障注入同一时间只由唯一执行者进行。

| 前置已通过 | 可同时进行 | 汇合卡 |
|---|---|---|
| S1-01 | S1-02、S1-03 | S1-04 |
| S2-02 | S2-03、S2-04 | S2-05 |
| S3-01 | S3-02→03→04 与 S3-05两支 | S3-06 |

其余卡按现有依赖执行。这个判断来自当前DAG和目录边界，不表示多人不能从事资料核对、测试设计或其他已授权准备工作。不能据此宣称工期减半；收益取决于两支实际耗时与集成成本。

## 4. 如果想让模型/界面更早并行

可以另行明确安排以下准备工作，但它们不是编号产品卡已开工或已验收：

| 准备线 | 可以产生的输入资料 | 不能替代的门禁 |
|---|---|---|
| 模型资料/离线验证准备 | 权重/类别/预处理核对、独立测试集方案、转换环境差异清单 | S2-09/10正式制品与实跑、相机/板端验收 |
| 客户端设计准备 | 页面/状态/错误交互、已冻结API消费表、正式fixture需求 | S3实现/登录TLS/实物借还 |
| 硬件资源准备 | 官方原理图比对、接线候选与冲突表、测量步骤 | 未验证profile不能驱动、SWD/电平/硬截止实测 |
| 回归设计准备 | 根据既有验收列成功/失败/断线/重启场景，定位测试层 | 未运行的测试不写PASS |

默认只读和文档准备不占用生产实现目录，不改stage-plan；若要提前写客户端代码/转换制品，应先把开发前置与最终实物验收前置重新拆清、由负责人同步任务卡/契约/检查器/指令包。不能把“准备”作为绕过原门禁的别名。本文没有自动增加新的产品卡或授权跨阶段实施。

## 5. 每组并发如何实际交接

开始前由M发布一次分配：卡号、真实已通过前置、允许文件、共享文件只读、接口版本、报告目录和汇合卡。A/B各用本卡既有开发指令，不使用另一分支的报告目录。

以S1-02/S1-03为例：

```text
M：确认S1-01已验收，冻结公共类型/队列/生命周期/依赖与根构建。
A：只开发S1-02；写stage-01/S1-02的summary/handoff。
B：只开发S1-03；写stage-01/S1-03的summary/handoff。
R：对已停止修改且标明代码指纹的交付审计；有问题回原分支整改。
M：在两支均通过后整合局部构建，跑跨模块相关检查并核对真实状态。
M：确认S1-04的全部前置通过，再发S1-04；缺任何一支不发。
```

无Git隔离时，两开发只能改不重叠目录；集成文件改动先排队交M。若后续采用分支/独立工作目录，每支同样冻结契约，集成后重验；不能声称当前已经建好分支或隔离环境。

审计发现共享契约缺陷，暂停受影响的两支入口，由负责人统一修真源/生成物/消费者/正式测试。无关部分可继续，但不能各自创建一套同名字段。审计/整改/交接仍使用本卡4段指令；状态写入始终一个负责人。

## 6. 正式启用前要统一的状态机制

当前check_stage_plan要求ONE_CARD_AT_A_TIME，且active_task只允许一张IN_PROGRESS；所以本方案暂不改变执行能力。不能只改字符串或直接标两张IN_PROGRESS。

启用受控并发应由一次统一变更完成：

1. 定义有界并发策略/最大2张，以及active_tasks列表与旧active_task的兼容规则。
2. 检查每张前置DONE、跨阶段门禁PASS、两张互不依赖、目录无重叠、共享写者唯一。
3. 检查器增加合法并发正例和未过前置/同目录/共享文件冲突/超额并发负例。
4. 同步stage-plan、模块所有权、执行手册、45卡指令生成器和打包资料。
5. 保留实际正在执行卡/已有证据，只在真实前置成立后调度下一组；不把模型或硬件未测条件改成通过。
